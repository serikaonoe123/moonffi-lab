# 编译期适配器

一个运行器由 `core`、`runner` 和适配器编译而成。两个实际入口分别见 `cmd/buffer-lab` 与 `cmd/eigen-lab`；`cmd/reducer-probe` 是用于验证缩减边界的合成测试程序。

需要从外部项目接入时，从 [SDK 指南](SDK.md) 和[独立起步模块](../examples/adapter-starter/README.md)开始。该模块只消费公开的 core/runner；验收在没有 Buffer/Eigen/引擎命令的新工作区中构建，不依赖 whitebox 访问引擎。

实现 `core.Adapter` 的以下职责：

| 方法 | 约定 |
|---|---|
| identity / version | 稳定身份和适配器格式版本 |
| validate | 从初始纯模型校验完整轨迹及参数，不执行原生调用，不改变工作状态 |
| execute | 在工作进程执行一步，更新实际状态和参考模型，返回可观察的性质失败 |
| teardown | 清理仍保留的对象，完成适配器有能力观察的检查 |
| shrink_arguments | 返回有限的、更简单的参数候选，保持步骤 ID、操作和对象依赖不变 |
| repair | 对删除后的候选运行新的纯模型，只删除无效步骤，并返回每步的删除原因 |

构造适配器时也不能触发受测调用，模块初始化同样需要保持纯逻辑。父进程只创建适配器、校验轨迹和生成候选。新工作进程会创建新的适配器实例。

每个 `Step` 有稳定 ID、操作名称、JSON 参数及 defines/uses/releases 三组逻辑对象 ID。引擎检查对象构造和使用顺序；适配器必须进一步检查声明与实际操作相符、尺寸与索引合法、错误输入属于 API 承诺处理的范围。稳定对象 ID 不能释放后再复用。

失败包含稳定 property ID、当前 step ID 和可读说明。缩减匹配 `property:<property ID>:<step ID>`，消息文本不参加指纹。指纹表示同一已声明性质在同一步骤失败，不是同一底层根因的证明。teardown 失败使用保留名称 `teardown`。

生成器是 `(UInt64, String, Int) -> Trace`；CLI 的三个参数对应 seed、fixture 模式和最大步数。使用确定性随机状态并限制对象、步数和数据大小；原始具体数据必须能无损序列化。各生成器的长度上限都不会超过 CLI 的 `--steps`。

`runner.cli` 还接受可选 `generators` 映射，将名称关联到同类型的纯生成器；`--generator NAME` 在 run/generate 时选择，默认名称 `default` 使用原回调。Buffer 和 Eigen 均注册了 `stateful`，分别标记 `generator_version=buffer-stateful-1`、`eigen-stateful-1`；后者依当前矩阵形状选择合法索引及不兼容加法。新增该映射不要求修改 Adapter 或核心类型；名称不可替代保存在轨迹中的具体步骤。replay/shrink 拒绝 `--generator`，防止把保存输入重新解释成另一套生成结果。

Eigen 另注册 `arithmetic`（`eigen-arithmetic-1`），依形状及保守数值上界生成合法 Add/Mul。适配器使用 Int64 精确整数模型，并在每次变更后核对所有存活矩阵。数值域、独立 oracle 与限制见 [算术实验](EIGEN-ARITHMETIC.md)。

运行入口调用 `runner.cli(args, make_adapter, generate)`，捕获顶层错误后用退出码 2 结束。不要在工厂函数或父进程读取/修改目标原生资源。`--worker` 是内部调用入口，用户通常使用 run/generate/replay/shrink。

适配器验证版本不匹配时应明确拒绝。核心 schema 当前为 1；重放读取保存的具体轨迹，不重新解释 seed。`environment` 保存 fixture 模式和检测 profile；Eigen 还记录绑定和头文件版本。完整工具链与二进制哈希由验收脚本的 `verification.json` 记录，直接单次 CLI 输出尚不自动补全这些环境信息。

参数缩减由公开的纯 MoonBit 函数 `core.arguments_simpler(candidate, original)` 限制进展。JSON 编码更短时沿用原规则；编码等长时，要求数组长度、对象键集合和非数值叶子保持一致，每个变化的数值必须是十进制整数且绝对值严格下降，其他数值保持编码相同。因此允许 `9 → 0`、`-9 → -1` 及其嵌套形式，拒绝 `[9,0] → [0,9]`。对象键顺序不参与比较。

需要整数候选时，可在 `shrink_arguments` 中调用公开的 `core.shrink_int(value : Int) -> Array[Int]`，再映射回保持身份与依赖的步骤。它先尝试 0，再尝试逐步靠近原值的候选，包含向零相邻的整数；例如 `200 → [0,100,150,175,188,194,197,199]`。0 返回空数组，每次至多 32 项，非零候选保持原符号且绝对值严格下降，支持 Int 的完整 32 位范围。它不修改 JSON 排序规则，也不会自动选择应缩减的字段。

候选仍须经过适配器完整验证，并由真实工作进程确认原失败指纹。比如计数器的越界加法不能缩成合法加法，初值归零也可能使人工缺陷不可观察。重复枚举能逐步逼近单调失败阈值；任意非单调性质仍可能停在局部结果，不保证参数最小。SDK 示例用此函数缩减构造值、加法量和拒绝加法量。

整数按十进制数字比较，支持超过 Int64 和 Double 精确整数范围的原始 JSON 表示。等长小数或指数编码没有专门下降规则；解析器已规范化成整数编码的数值按实际编码判断。长度严格下降，或等长且有限个整数分量逐项下降，使已接受结果不会形成循环；这不保证搜索穷尽或参数最小。适配器仍须返回有限候选数组，缩减器相对于最新已接受参数检查候选，跳过重复及反向变化。

每次接受参数变化后，缩减器丢弃旧候选列表，从当前轨迹重新枚举，因此单级候选也能逐级执行 `9 → 4 → 2 → 1 → 0`。一轮参数枚举无变化后，检查单步删除；接受删除后再次枚举参数，允许步骤删除解锁先前被拒绝的更早参数。纯修整删除前序步骤后也会重新定位，避免沿用旧索引。所有新尝试共用原执行/墙钟预算，预留最后三次确认。

`Reduction.argument_search` 是可选的进度对象：`passes` 计数已启动的参数扫描轮次，`candidates_checked` 计数最终轨迹当前扫描中查看过的候选（包括重复、不下降及非法候选），`complete` 表示这轮候选已枚举完且没有可接受变化，`inconclusive_candidates` 记录该轮的工作进程异常或错误修整等未决结果。接受变化后，旧轨迹的候选计数与完成状态失效；预算可以留下稳定但尚未完成搜索的部分结果。旧 JSON 报告可继续读取，此字段缺失表示未记录，不能解释为已完成。

`search_complete` 现在要求参数枚举及最终单步删除检查均完成。适配器不必枚举全部更简单数值，已枚举候选也可能有未决结果，所以此状态和 `argument_search.complete` 都不提供参数最小性保证；`deletion_minimal` 仍只说明声明策略下的删除邻域及最终稳定性。

`Step` 的相等判断也使用精确参数表示，不沿用 JSON 的 Double 数值相等；因此修整检查能区分 `9007199254740992` 和 `9007199254740993`。对象键顺序不影响相等，不同数值编码则保守视为不同具体输入。

数组长度、尺寸等变化还须通过完整纯模型验证；更简单的候选若不再保持失败指纹，也不能被接受。缩减器当前只自动处理可识别的行为性质失败，其他结果保留证据而不接受为等价反例。

## 状态修整约定

2026-10-17 的开发版本新增必需的 repair 方法。简单适配器可直接调用 `core.repair_dependencies(trace)`，只处理对象可用性。合成边界探针使用该实现，并继续通过自己的 validate 校验语义。Eigen 已改用状态模型：删除写入后可能使后续算术超出精确整数域，不能只检查依赖。

需要语义修整时，实现 `core.StateModel.apply(step) -> String?`，再调用 `core.repair_with_model(fresh_model, trace)`。apply 接受一步时更新纯状态；拒绝时返回原因，必须保持状态不变。每次调用 repair 都使用全新模型，不能复用工作进程模型。

Buffer 示例将多个逻辑句柄映射到同一 BufferState。Resize 改变该资源的长度与数据，因此经其他别名进行的 Write 也按新的长度检查。若删除 Resize 使后续 Write 不合法，修整会删除该 Write；后续步骤仍按保留下来的状态演进。拒绝写入不改变正确参考模型。

引擎独立检查 repair 结果是原候选的子序列、顺序和具体输入不变、metadata 不变、每个删除恰有一条非空说明，并再次完整 validate。修整不得凭空补步骤、修正数值、重命名对象或替换失败类型。参数候选还必须保留被修改的步骤。错误修整器不能获得 deletion_minimal=true。

通用依赖检查和修整现在共用增量索引：每步先检查身份与依赖，再调用模型，只有模型接受后才提交步骤 ID、历史定义及存活句柄变化。模型拒绝释放不会关闭句柄，拒绝定义不会占用名称；结构检查后期失败也不留下部分变化。诊断优先级与旧前缀算法保持一致，修整的 4096 步限制仍按保留下来的步骤计数。

依赖索引对每个步骤及句柄声明/引用做固定次数的检查，在哈希表平均开销下随输入规模线性增长；删除解释覆盖检查也改用 ID 索引，并保留原有重复/缺失诊断。这不包括适配器模型、字符串哈希及具体参数比较的成本。CLI 生成最多 256 步，直接依赖接口最多 4096 步。

增量索引只保证引擎自身依赖状态在拒绝后不变，不能回滚不透明的适配器模型。尚未将复杂模型视为不可信代码，也不能强制阻止适配器违反“拒绝不得变更状态”的契约；仍须通过适配器测试验证。
